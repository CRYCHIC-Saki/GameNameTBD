# Phase 4｜雇员与第二家店

现在执行 Phase 4：中期经营扩展。
读取总控协议、前序版本和反馈，执行 Grill Me。按4A→4B顺序实施；4A工程检查通过后可继续4B，不必每个文件都等我确认。

目标：让雇员释放玩家精力，让第二家店产生不同的经营决策，而非简单增加收益倍数。

Grill Me优先解决未定的托管边界、分店结算周期、共享资源与店铺独立资源。技术实现自行决定；不要再次询问已确认的首发范围。

4A：单店雇员
1. 先选一种能够替代已有操作的岗位，例如已存在切菜系统就先做备菜岗；不能为了一名打杂员工临时堆出一整套无关杂务。
2. 实现雇佣、解雇、分工、工资、熟练度与有限的品质/事故差异，随后按本阶段范围加入主厨和店长。
3. 员工执行也通过现有库存、工序与订单规则，不从界面凭空发出一份完美菜品。
4. 玩家亲手操作与托管互斥或按明确规则接管；同一工序不能两边同时执行。工资按统一游戏日历结算，不能混用月薪与日薪。
5. 测试玩家不雇人仍能经营；雇人后成本和节省的操作都能真实观察。

4B：第二小镇与第二家店
1. 只新增一个具有不同已配置饮食偏好的小镇和一家分店；地点与数据映射须明确，不能按相似名字偷偷合并设定。
2. 实现开店条件、店长、菜单、价格、员工、自建食谱转移和分店结算界面。
3. 为每家店建立独立运行状态，明确共享资金/仓库与本店资源的边界。建议后台分店采用可解释的日结模拟，不复制完整实时QTE与顾客场景。
4. 模拟结果依赖菜单、偏好、供应、员工、价格和经营参数；展示收入、成本、损耗及事件原因。营业逻辑与离线/后台结算不应出现两套互相矛盾的核心规则。
5. 自建食谱带稳定ID与版本；决定更新时是保留快照还是显式同步，旧版本引用不可失效。
6. 对相同店铺和日期的结算进行去重；读档、切换店铺及重复调用不能刷收益或重新抽取已确定的事件。

验收：
- 原店仍可亲自经营，员工确实执行已有操作且工资准确。
- 两家店不共享可变菜品实例或意外污染菜单/员工状态。
- 经配置的同菜跨文化经营差异可复现并解释，调整定位后产生对应变化。
- 固定条件下可模拟至少30个游戏日；覆盖缺店长、缺货、资金不足、员工离开、重复结算、存读档和配方更新。
- 人工试玩验证玩家是否获得了“亲自做什么、交给谁、两店如何定位”的选择。

禁做：全部小镇、多店真实离线实时仿真、复杂供应链优化平台。
完成两家店的真实经营闭环后停止。
