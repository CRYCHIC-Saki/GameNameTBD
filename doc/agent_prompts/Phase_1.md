## 四、必做功能

### A. 数据、食材实例与配方定义

实现食材、食谱、工序、反应、QTE 参数和数值表的加载与校验，使用唯一权威的运行时数据源。JSON 或 Godot Resource 的选择遵循已有工程，不维护两份人工同步的权威数据。

食材定义至少覆盖大类、小类、品质、七味基准、三轴口感、带强度的香味、地域标签和特殊属性。运行实例独立保存份量、细碎度、切型、温度、已处理历史及所需的暴露/加热时间。份量单位及聚合算法需明确，不假装原文已有公式。

食谱定义至少覆盖稳定 ID/版本、必需食材及替代匹配规则、细碎度约束、必需工序、理想口味区间、温度区间、口感与香味要求、官方/自建身份。区分“食谱要求”与“推荐制作方案”：食谱不是把玩家锁死的关卡脚本。

同大类替代可补位，但保留实际用料的风味、品质和地域差异。必需项匹配使用显式规则，不靠显示名称模糊猜测，也不把缺少字段当成“无要求”。

每份食材、半成品、菜品和会话有清楚的身份与归属。支持分开处理食材后合并；不能切番茄时连鸡蛋的细碎度一起改变，不能把某食材加入前发生的受热/切割历史倒算到它身上。

读取和使用模板不得修改共享定义。校验重复 ID、引用缺失、非法枚举、矩阵形状、范围倒置、负份量、非有限数值与不受支持的操作；错误包含来源文件和字段位置。只校验/装载当前启用集合，未整理的候选小镇资料不伪装成可运行内容。

### B. 六项菜品属性与可解释计算

完整实现：
1. 口味：酸/甜/苦/辣/咸/鲜/麻 × 前味/主味/余味/回味，28 个强度值；主导味和超过阈值的复合味分开，处理并列与空味型。
2. 温度：加热、环境冷却、经过时间和容器参数。自然冷却按大纲的指数形式实现，并支持恒温参数；40℃/65℃附近与冷菜、负温度数据不得被热菜假设误判。
3. 香味：有强度的标签集合，支持获得、变化及负向香味；无香惩罚、理想香型加成由已确认规则统一计算。
4. 口感：硬—嫩、韧—脆、弹—粘三条轴，保留定义方向；单个食材的要求可从处理记录解释，不能全部丢进一个无法追踪的平均值。
5. 完成度 Q：按大纲的工序表现加权、品质加成、额外食材/工序代价、缺失必需项规则及自建食谱规则计算。区分额外工序数与额外食材数；处理空工序和总权重为零的情况。
6. 搭配度 H：使用配置化口味关系与五档基础分，结合香味、口感和勾芡等效果；不能写成固定常量，也不能只让 QTE 平均分代替搭配度。

基础属性、不可逆处理变化、当前温度造成的感知修正分开计算。显示刷新、重复查看结果或重复评分不得持续放大口味、重复扣 Q/H、重复产生反应。不要在每帧对“上一帧已修正结果”反复套相同倍率。

Q/H 的应用次序、范围截断、额外操作计数及无香/缺失惩罚不得在多个模块重复实现。所有新增数值外置并标记来源/建议值。调试视图能显示主要变化来自哪份食材、哪道工序或哪条规则。

### C. 自由工序与完整处理链

用明确的工序定义、前置条件、目标对象和有序 Modifier 实现处理链。选择目标食谱后，玩家仍能选择用料、改变允许的先后顺序、追加调味/处理、暂停/继续、放弃或重新做，而不是只能点“下一步”。

实现下列处理机制，并接到真实 CookingSession，而非只有孤立函数：
- 切菜：节奏、旋转/切型、片/块/条/丁、逐食材细碎度、前味与余味变化；“切得更细”与“按得更准”是不同维度。
- 预热/点火、翻炒/搅拌、投料/调味、控温、出锅等可复用操作。蒸/炖等共享控制方式可以参数化，不要求给每个菜名写新小游戏。
- 加热与时间的属性变化，以及美拉德、焦糖化、蛋白质水解、脂肪氧化四种大纲反应。
- 勾芡、发酵、切开后久置氧化，包含各自条件、持续时间与真实属性后果。
- 出锅后的等待/冷却、必要的保温，以及交付前再加料、复热或其他允许的二次加工。
- 半成品的分开处理与合并，支持不需要切菜、无需加热、冷食或不同工序组合的配方表达，不默认每盘菜必须走番茄炒蛋流程。

每条反应定义条件、检查时点、一次触发或持续累积语义、重置规则和事件记录。没有糖/肉类等前提时，不得仅因 QTE Perfect 就发生相应反应。重复触发与同帧多次回调不得刷香味或搭配度。

区分“系统不合法”和“菜可能不好吃”：例如不存在的食材引用应拒绝；没有按食谱做却仍可形成菜品的情况，按确认规则降品质/判不成菜，而不是全部禁止。已经执行的工序不能靠重排历史或撤销界面无成本恢复原料。

处理欠火、过火、切菜失误、原料不可用、缺失必需项与放弃；切伤的时间/SAN 影响按来源与确认参数记录。二次加工沿用同一实例历史，不能洗掉烧焦、氧化或旧的完成度代价。已交付/报废实例不可再次加工或交付。

### D. 五类 QTE 全部可操作、可复用

五类必须都有实际输入、运行过程、判定和与工序的联动，不接受空壳、直接弹成绩或仅实现三类：

| 类型 | 必须实现的操作与反馈 |
| --- | --- |
| 蓄力型 | 按住累积，在目标区间松开；有过早、命中、过冲、超时与取消结果 |
| 节奏型 | 依据节拍处理多次输入；覆盖切菜/翻炒等配置，有漏拍、错拍、连击与多余输入处理 |
| 窗口型 | 在指定时间窗口输入；有过早、过晚、未操作和正确命中 |
| 维持型 | 连续控制量抵抗扰动，累计目标区间内表现；不是换皮的单次窗口判定 |
| 顺序型 | 按配置顺序输入/投料/调味；明确错误、重复、遗漏与超时的处理 |

统一生命周期：开始、接收输入、更新时间、完成、取消、复位；返回结构化结果，包含会话/工序身份、表现、必要时间信息和失败原因。名称与协议实现顺应已锁定的 Godot/GDScript 能力，不照抄其他引擎接口语法。

Perfect/Good/Miss 参数化。±60ms/±140ms 只作为大纲的建议时间窗，不能机械地套到温控数值、蓄力数值或顺序准确率；非时间型 QTE 的分档依据单独记录。

使用 InputMap、可注入的逻辑时钟和随机源；不以渲染帧数、按键自动重复次数决定结果。明确暂停、失焦、长帧、输入迟到、取消与恢复规则，并测试边界。提供音画/输入偏移参数，真实设备校准与试听另行验收；自动输入测试不代表手感通过。

### E. 双菜并发

在同一个可玩厨房中同时运行两个会话；可以使用同一食谱的两份独立实例，不需要额外正式菜谱。

实现两套 QTE 的同时显示与运行、各自工序选择、目标身份、计时、操作、失败和出锅。按大纲采用主菜 WASD、附菜方向键的默认思路，并通过 InputMap 明确单菜切菜空格与双菜模式的映射关系；已有确认键位优先。

输入必须路由到明确槽位/动作，不能一次事件被两个会话意外重复消费。需要共享动作时必须显式定义。测试同一帧两侧输入、按住一侧操作另一侧、单侧完成/取消与另一侧继续、暂停恢复及调试焦点切换。

“双菜并发”是两个会话真正并行推进，不是快速切换两个暂停中的页面。两侧不能共用可变食材、计时器、QTE 结果或业务随机状态；一侧重开不重置另一侧。分别覆盖逻辑隔离测试和双 QTE 场景集成/实机输入测试。

### F. 自由摆盘、成品与交付边界

提供基础可交互摆盘：玩家可移动/排列食物，盘内合法摆放不加分、不扣分；按确认的越界/倾倒规则处理倒出去和失败。不能用“点击确认”按钮冒充自由摆盘，也不做复杂真实流体。

视觉位置变化不改变口味、香味、Q/H 或质量。倒出/报废产生明确结果，不重复生成成品。只有已确认的特殊食谱例外才可改变通用评分规则。

完成后输出独立菜品结果/快照，包含属性、真实用料与工序摘要、配方身份、有效性/失败原因和必要的追踪信息。交付动作只在烹饪边界结束并发出结果事件，不直接改金钱/声望。

每份成品只允许交付一次；重复点击、重复信号和过期回调不能产出第二份。提供交付前二次加工与交付后拒绝修改的验证。

### G. 自建食谱的烹饪侧闭环

实现最简但完整的创建、命名、修改/另存版本、校验、保存、读取、选择和重新制作。允许由本次用料与处理方案整理成自建配方，并保留官方/自建身份与相应限制。

保存的是食材/份量/步骤/参数方案和约定的目标信息，不是一次 Perfect 的输入录像、满意度或可直接领取的高分成品。重新制作必须重新消耗本次原料、执行工序并计算结果；保存、命名和重新打开不能提高当前菜品分数或把自建身份改成官方。

把本地配方库持久化接到项目已有存储设施；没有设施时用小型版本化存储，并在后续经营存档中复用。不在本阶段实现任意 QTE 中断现场存档、全局日期或店铺存档。

实际测试读写往返、坏文件、未知版本、缺失引用和写入失败；测试目录隔离，不覆盖真实数据。测试配方不能流入正式配方目录/正常菜单。满足条件的预设识别/解锁依据配置记录，不能写成“菜名叫番茄炒蛋就解锁”。

### H. SAN 的烹饪侧机制，不扩展整个 SAN 成长线

以下必须实际生效，而非只留接口：
- 接收当前 SAN 上下文，按已确认策略改变适用 QTE 的判定参数。
- 低 SAN + 符合条件的 Perfect，在存在候选变体时按配置概率生成阴暗版本；候选条件、抽取时点、触发单位和失败回退可解释。
- 产出变体身份、变化后的结果以及一次性的解锁/产出事件；正常输出和阴暗输出不能同时重复发放。
- 使用可控、与视觉随机隔离的业务随机源，重看结果和重复回调不重新抽取；有成就所需的事实事件，但不在此做完整成就系统。

当前 SAN、食谱 Tier、制作/交付 SAN 消耗、变体生成概率是不同概念，不能互相替代。消耗只在确切事件按规则计算一次，并输出给外层接入。

高 SAN 正常描述与连续缩放公式冲突时先按决策确定策略；不得静默挑一版。原始低 SAN 分级未统一时保留来源，不把某套建议值伪装成统一标准。

测试厨房可直接设置 SAN，用一份明确标注 TEST_ONLY 的变体配置验证结果。没有给番茄炒蛋规定官方阴暗版本时，不自行宣称某个变体已被策划确认。完整 SAN 获取/恢复的生活循环、持续多日状态、主线入口及正式异常美术留给后续阶段。

### I. 独立评分与反馈试验台

实现/复用独立 CustomerScorer。它读取菜品结果及声明要求，输出满意度、星级和逐项解释，不属于 CookingSession 内部，不反向修改菜品。

至少提供两组对番茄炒蛋有不同明确要求的试吃配置，例如甜口大块与另一种已配置偏好。同一份结果可以只读地比较两组要求，这种测试不意味着一份菜能在经营中出售两次。

只对声明的维度施加需求偏差；区间内偏差为零、区间外的归一化与权重规则明确。食谱必需项、基础 Q/H 规则和顾客要求分开，避免重复扣分；食材/工序/细碎度的声明也不能在评分时被静默丢弃。

以大纲 §3.7 的满意度公式为基线，变更需明确记录。不得用 Onboarding 中“88 分/三星/小费 +8”倒推出一套硬编码评分；未给全的分档、归一化和附加要求计算列为建议值/决策。试吃器不发真钱或经营奖励。

### J. 集成可玩的开发厨房

从工程入口可进入完整开发厨房，至少支持：选择目标食谱或自建方案、选择/替换食材、选择目标食材与工序、实际操作 QTE、查看当前加工状态、单/双菜切换、二次加工、摆盘、交付试吃和重新开始。

提供机制测试入口来覆盖番茄炒蛋未使用的反应/QTE；这些入口必须复用正式运行逻辑，不能另写一套只供演示的简化模拟器。测试料盘可提供有限批次原料并记录用量，不等于本阶段要做采购经济。

信息分为正常操作反馈与可展开的调试详情：正常界面能理解选择、成功/失败和差评；调试详情能查看 28 维、三条口感轴、温度、香味、Q/H、逐步变化、反应与参数来源。不能要求用户靠控制台命令完成日常试玩。

使用明确标记的占位美术/声音，不因缺正式资产停在纯数据层；最终画风、长篇教程与街区由 Phase 3 打磨。

## 五、通用性必须通过反证测试

不接受“放了 JSON 文件，所以数据驱动完成”。必须用同一系统证明：
1. 番茄炒蛋定义从普通数据加载；核心计算、状态机、QTE 和评分不得按该菜名/ID写特殊分支。测试断言和内容清单引用其 ID 是正常用法。
2. 仅增加一份开发专用配方数据，就能完成“加载 → 选择 → 制作 → 出结果 → 试吃”，不修改通用核心逻辑。该配方至少在工序结构或温度需求上与番茄炒蛋明显不同，不只是改名字。
3. 再用必要的测试夹具覆盖剩余机制，例如无加热组合、发酵、勾芡、四种反应和不同 QTE 组合。夹具只为覆盖，不批量制作正式食谱。
4. 每类 QTE 均至少接入一次真实工序；每种必做处理/反应均具有可达的正例、反例和边界测试。
5. 修改测试配方的材料、份量、顺序或参数，会通过相同模型改变结果；不能读取配方中的“预设最终分数”直接显示。
6. 清楚说明配置能力的边界。新操作或新语义未实现时报告不支持；不靠任意脚本执行、字符串求值或万能条件引擎冒充支持所有未来菜谱。

## 六、Godot 与软件工程约束

沿用 Phase 0 锁定的引擎、语言、渲染器、测试框架和工具版本，不擅自升级。需要使用具体 API 时查锁定版本的官方文档并实际运行，不假定伪代码就是合法 GDScript。

按实际职责拆模块：食材/配方数据、CookingSession、工序与反应、属性求解、QTE、双菜协调、配方持久化、独立评分及表现层。类名顺应现有工程，不强制制造所有 Manager，也不把模块都设为 Autoload。

界面只发意图，规则层检查合法性并更新状态。场景释放、取消、重新开始和过期异步回调需要清理；结果事件携带会话/工序身份，避免上一次操作误作用到新菜上。处理日志用于调试和复现即可，不因此建立全项目事件溯源平台。

跨模块约定明确输入输出与失败语义。后续库存接入应当从真实用料/用量记录消费，后续经营从成品事件接入结算，不能让界面和规则层各扣一次。当前只实现足够验证这些契约的测试适配，不开发整套经济系统。

关键规则先写可观察 AC 与失败测试，再小步实现。测试预期来自手算样例、独立参考或性质断言，不能只是再次调用同一生产算法后与自己对比。浮点容差和时间精度明确。

复用现有检查入口与 CI，真实报告导入、脚本/资源加载、单元测试、场景集成和实际可运行状态。不得通过删测试、跳过必测项或缩减验收范围掩盖失败。保护用户未提交改动，不进行破坏性 Git 操作或擅自推送/发布。

## 七、阶段内部实施顺序

以下是同一个 Phase 1 内的工作单元，不是让我逐段重新发送的七份 Prompt：

| 单元 | 实施内容 | 本单元结束时的实际结果 |
| --- | --- | --- |
| 1A | 检查既有工程、范围修订、Grill Me、数据模型与最短纵向通路 | 普通配方数据可载入，初版会话可经过一种真实工序形成结果并独立评分 |
| 1B | 六项属性、自由工序、食材实例、处理与反应 | 属性变化、条件触发和历史可解释，番茄炒蛋能在开发厨房制作 |
| 1C | 补齐五类 QTE、统一生命周期、计时与反馈 | 五类均可实际操作且接入真实工序，不只是调试返回成功 |
| 1D | 双菜并发、二次加工、自由摆盘与交付保护 | 两道菜能同时推进，完整走到摆盘/交付/重试 |
| 1E | 自建食谱、持久化、SAN 烹饪侧联动 | 配方可保存重做，SAN 与阴暗产出可独立验证 |
| 1F | 通用性测试、开发厨房整合、对外契约 | 新的 TEST_ONLY 配方仅靠配置运行，经营接入不依赖菜名 |
| 1G | 全量回归、缺陷修复、覆盖审查、人工试玩交接 | 逐项区分通过、失败、未验证，形成阶段交付报告 |

可以按真实依赖细调顺序，但不能省略单元。每个单元接入可运行工程，进行自动检查；没有阻塞时继续下一个，不逐文件请求批准。中断时记录当前单元、未完成机制、下一命令/任务和真实测试状态；不能把 1B 完成说成 Phase 1 完成。

## 八、最低验收矩阵

将下表转成工程内可追踪的 AC，保留必要的更细测试。所有“通过”都必须有实际证据。

| AC | 必须证明 |
| --- | --- |
| AC-PHASE-1-001 数据契约 | 矩阵/范围/ID/引用/枚举/份量错误可定位；缺失内容不静默伪造；只装载启用内容 |
| AC-PHASE-1-002 实例隔离 | 同模板的两份食材和两个会话互不污染；番茄的切型不改变鸡蛋；模板始终不被加工修改 |
| AC-PHASE-1-003 属性计算 | 六项属性均由规则产生；边界、空值、并列味型、零总权重与范围截断有测试；评分/显示只读 |
| AC-PHASE-1-004 处理顺序 | 在已定义的非交换操作案例中，改变顺序产生可解释差异；推荐流程之外仍可操作；非法操作拒绝后状态不半更新 |
| AC-PHASE-1-005 反应完整 | 四种加热反应及勾芡/发酵/久置氧化均有正例、反例与边界；不满足前提不触发，重复回调不刷效果 |
| AC-PHASE-1-006 时间一致性 | 同一逻辑时间线在不同更新切分下得到约定容差内结果；冷却、热处理、反应不按显示刷新次数叠加 |
| AC-PHASE-1-007 QTE覆盖 | 五类均有真实输入和场景集成；开始/完成/取消/复位、Perfect/Good/Miss或对应分档、超时与重复输入有验证 |
| AC-PHASE-1-008 时间与输入边界 | 窗口两端、自动重复、同帧输入、长帧、暂停/失焦/恢复、旧回调不影响新会话；真实音画校准另记状态 |
| AC-PHASE-1-009 并发 | 两个 QTE 同时运行；两侧操作路由正确，单侧失败/取消不重置另一侧；独立时钟状态与随机状态不串用 |
| AC-PHASE-1-010 返工与失败 | 交付前可二次加工并保留旧变化；欠火/过火/缺料/缺必需项/放弃结果明确；已交付或报废不可复用 |
| AC-PHASE-1-011 摆盘 | 盘内位置变化不改分；倒出按规则失败；交付及报废事件不重复发出 |
| AC-PHASE-1-012 独立评分 | 同份结果对两组不同要求产生可解释差异；未声明维度不扣需求分；食谱惩罚与顾客偏差不重复应用 |
| AC-PHASE-1-013 自建配方 | 保存/命名/修改版本/重载/重做全流程通过；重做重新判定，不能保存成绩刷满分；坏文件与未知版本安全处理 |
| AC-PHASE-1-014 SAN | 边界 0/30/60/100 按选定策略；无候选/不满足资格/概率0与1/固定种子可验证；多次读取或回调不重抽或重复扣SAN |
| AC-PHASE-1-015 数据扩展 | 一份明显不同结构的 TEST_ONLY 配方仅改数据即可完整制作；核心无番茄炒蛋特判；剩余机制有独立测试覆盖 |
| AC-PHASE-1-016 稳定生命周期 | 连续重开、取消、换配方、进出厨房后无重复信号、残留计时器、旧输入或测试内容误入正式内容 |
| AC-PHASE-1-017 外部接入 | 测试适配器可以供料、接收唯一成品与事件；做菜与评分不直接改金钱/声望；实际用料有可核对记录 |
| AC-PHASE-1-018 工程证据 | 检查命令、引擎/依赖版本、测试发现数/执行数/通过失败数/退出码真实记录；无测试、必测跳过、解析失败或超时不算通过 |

人工试玩至少覆盖：普通番茄炒蛋；改变切型/调味/火候后根据反馈改进；五类 QTE；双菜并发；自由摆盘与失败；自建食谱重做；SAN 测试。准备可重复的短操作路径，不要求玩家阅读开发规格才能体验。

无法运行 Godot、图形窗口、音频或真实输入设备时，继续完成不受影响的工作，但对应项标记 NOT_RUN/BLOCKED，不假称实测。机器检查通过不代表玩家已认为好玩；无人试玩就写 PLAYTEST = PENDING。

## 九、交付与停止条件

交付必须包括：
1. 实际接入 Godot 工程的系统、场景、普通番茄炒蛋配方、必要测试配置与测试代码。
2. docs/systems/cooking.md 中的模型、状态、计算规则、数据扩展步骤及经营接入契约。
3. 阶段覆盖表：每种必做机制的入口/代码/测试/实际结果；未实现或未验证项不得藏在“后续优化”里。
4. 真实启动与测试命令、测试结果，以及不超过五步的总试玩路径；各专门机制可在试玩说明中给子入口。
5. 关键范围/规则决定、仍未定的参数、已知风险、断点和后续阶段的依赖变化。

报告工程实现、自动验证、目标设备与人工玩法验收四种状态。全部必做机制接入并达到对应检查门槛后，才可标记本版工程完成；尚缺人工试玩时明确交付“工程就绪、待试玩”。

不要自动开始 Phase 2。最终目标是：**番茄炒蛋证明第一张食谱能跑；测试配方与覆盖矩阵证明系统不是只会做这一道菜。**
