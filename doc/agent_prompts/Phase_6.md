# Phase 6｜测试、兼容与发布候选版（v3 总方案）

> 当前状态：规划中。必须在 Phase 5 首发内容冻结、食品品牌终局可达后执行。
>
> 总流程：`docs/FULL_IMPLEMENTATION_FLOW.md`
> AI 补充：`docs/AI_FILLED_DETAILS.md`
> 本阶段授权本地构建，不授权推送、对外发布、上传商店或修改全局环境。

## 1. 目标和入口审查

目标是产出可重复构建、范围明确、证据充分的 Windows 发布候选版。

阶段入口只核实：

- 实际支持的 Windows 版本和测试硬件；
-【AI填充细节 AI-031】的性能目标是否维持；
- 从哪些旧存档版本迁移；
- 什么问题会阻断候选版。

不借发布阶段增加菜系、小镇、剧情、店型或经营系统。

## 2. Phase 6-0｜功能和内容冻结

1. 锁定 active 小镇、食谱、市场、NPC、事件、装修、成就和资产清单。
2. 给每项标记最终、占位、开发专用或延期。
3. 删除正式入口里的跳转、测试开关和未批准内容；保留开发分支所需夹具但不导出。
4. 记录源代码提交或完整工作树差异、引擎、插件和导出模板。

缺陷按以下优先级处理：

1. 崩溃、坏档、品牌终局不可达；
2. 无限钱/物、负库存、重复解锁、重复领奖和读档重抽；
3. 订单、员工、研发、市场和事件的交互阻断；
4. 可读性、手感、性能和视觉问题；
5. 不影响流程的装饰瑕疵。

每个修复先复现，做最小修改并补回归。不能靠降低 AC、删测试或把已承诺功能改写为延期来通过。

## 3. Phase 6-1｜自动检查矩阵

### 内容和资源

- 导入、脚本解析、生产资源加载；
- 食材、食谱、调料、店型、市场、研发图、NPC、事件、成就和资产引用；
- 不可达研发节点、条件环、重复 ID、未来内容误入 active；
- 包内资源白名单。

### 规则和集成

- Phase 1 六项属性、五类 QTE、双锅和独立评分；
- Phase 2 库存、订单、日结、自建食谱和边界存档；
- Phase 3 小镇、客流、餐厅、客单、入座、传菜和分店；
- Phase 4 入锅变体、熟练、研发、三岗位、市场、店型、市政和供货事件；
- Phase 5 野采、报刊亭、特殊 NPC、轻量关系、PK、节日、摆盘截图、品牌、全球影响力、成就和可选低 SAN 小镇。

### 攻击性回归

- 重复交付、退款、日结、领奖、市场刷新和分店结算；
- 员工与玩家同时做同一工序；
- 研发取消、断电和重载后免费重试；
- 低 SAN 重复入锅或结果读取；
- 负库存、过期食材、免费自建配方和托管收益失控；
- 同一随机状态读档重抽；
- 篡改、缺字段、未知枚举和非有限数值。

### 门槛

`tools/check.ps1` 必须输出真实发现数、执行数、失败数、跳过数和退出码。以下都算失败：

- 零测试；
- 必测 pending/skipped；
- 解析或资源加载错误；
- 运行时报错或对象泄漏；
- 超时；
- 缺少测试报告。

同时保留故意失败、跳过、解析错误和零测试的门槛证明。

## 4. Phase 6-2｜存档兼容

分别验证：

- Phase 2 `shop-v1.json` 的合法旧档、损坏档和未来版本；
- Phase 4 新版世界存档的每个已承诺 schema；
- 旧岗位到三个岗位；
- 旧直接解锁到 AI-001 食谱状态；
- 市场、事件、分店、品牌和随机结果；
- 写入中断、临时文件、备份恢复和磁盘失败。

迁移前保留备份。迁移失败必须保留原档并返回明确错误，不能静默开新档。回退到旧程序可能无法读取新档，发布说明必须写明。

## 5. Phase 6-3｜目标机和人工验证

按【AI填充细节 AI-031】验证：

- Windows x86_64 启动和独立包运行；
- 1920×1080、窗口/全屏和常用缩放；
- 实体键鼠、输入重绑定、暂停、失焦恢复；
- 主音量、音乐、音效和耳机/扬声器；
- 减少动态效果不会改变 QTE 判定；
- 最大首发小镇、满客餐厅、双 QTE、市场和多日切换；
- 长时间营业后的内存、节点、输入和音频状态。

至少安排：

1. 一次新玩家引导试玩；
2. 一次连续三日主店经营；
3. 一次研发、市场、市政和员工试玩；
4. 一次从中期档推进到食品品牌终局；
5. 一次可选低 SAN 重演。

自动输入、开发者熟练操作和真人陌生玩家要分开记录。

## 6. Phase 6-4｜性能与稳定性

使用真实 Profiler 和日志，注明：

- CPU、GPU、内存、系统和引擎版本；
- 测试场景、时长和采样方法；
- 平均、低分位和最差帧时间；
- 内存起点、峰值和长时变化；
- 节点数、场景切换和加载时长。

先优化实际最大瓶颈。不得用空场景数字宣传正式体验，不得把“进程退出”写成“零泄漏”。

如果达不到 AI-031，给出真实测量、受影响场景、降级设置和新的最低配置建议；修改目标必须新增决定。

## 7. Phase 6-5｜资产、包体和合规

1. 核对每项资产的来源、许可证、修改方式和署名。
2. 移除未授权资产、未批准占位和不可再分发内容。
3. 检查包内没有密钥、真实玩家档、测试依赖、原始设计资料、开发作弊入口和个人路径。
4. 检查文案以菜和情境为笑点，不嘲讽地区、人群或疾病受害者。
5. 输出最终运行资源清单。

## 8. Phase 6-6｜可重复构建

1. 使用锁定 Godot、依赖和匹配模板；
2. 在无缓存、含中文和空格路径的干净副本导入；
3. 运行同一全量检查；
4. 构建 Windows 包；
5. 独立启动并走关键流程；
6. 记录构建命令、版本、文件哈希、大小和运行依赖；
7. 对比源工程和干净副本的生产输入。

能导出不等于目标机运行通过，两项分开报告。

## 9. 发布候选交付

交付：

- 发布说明；
- 玩家操作和设置说明；
- 支持平台、最低配置和已知限制；
- 存档兼容、备份和回退说明；
- 自动检查、目标机、人工试玩和性能证据；
- 资产许可证与署名；
- 发布包哈希和复现步骤；
- 未通过项和阻断级别。

## 10. 发布门槛

只有同时满足以下条件，才能写“发布候选满足门槛”：

- 没有已知崩溃、坏档、品牌终局阻断和严重经济漏洞；
- 自动检查全部真实通过；
- 声明支持的目标机关键流程实际运行；
- 存档迁移和中断恢复通过；
- 真人完成核心成长流程；
- 构建可在干净副本复现；
- 资产和包体审计通过。

缺任何一项，只能交付“发布候选，尚未满足发布门槛”。本提示词不授权正式发布。

- AC-PHASE-6-001：功能和 active 内容冻结，开发入口不进入正式包。
- AC-PHASE-6-002：全量自动检查、故障门槛和零跳过。
- AC-PHASE-6-003：所有承诺存档版本迁移、中断、备份和未来版本拒绝。
- AC-PHASE-6-004：目标 Windows 设备、实体输入、音频、显示和无障碍。
- AC-PHASE-6-005：最大场景、长时营业和真实性能证据。
- AC-PHASE-6-006：许可证、署名、敏感文件和运行资源白名单。
- AC-PHASE-6-007：干净副本可重复测试、构建、独立启动和文件哈希。
- AC-PHASE-6-008：真人核心成长流程、发布说明、已知问题和回退限制。

每项分别报告 `PASS/FAIL/NOT_RUN/BLOCKED/PENDING`，不得用一个总的“测试通过”覆盖未执行类别。
