- 一道菜完成 6 次后，普通制作不再出现 QTE；复杂 QTE 转移到研发。现有 QTE 还用于前 6 次、研发和后期低 SAN 重演。

- 官方菜谱先点亮、再研发、80 分解锁、最后才能上菜单，覆盖旧的总体评价 60 分直接学会。
- 低 SAN 小镇不是必经主线；它延后为重演前期做菜机制的可选后期内容。

## 3. 玩家从新档到终局的完整流程

1. 玩家在现代小镇开主店，完成取料、固定程序做菜、交付和日结教学。
2. 前 6 次制作一道菜时亲手完成 QTE，并从评价里理解切型、火候、调料、温度、香味和口感。
3. 第 6 次合法成品后该菜熟练。以后普通营业自动走固定程序，不再重复相同 QTE；玩家的操作重点转向订单调度、原料、菜单和经营。
4. 玩家从升级、做好菜和事件中取得研发点，先在中式、英式或印度食谱图上点亮目标，再进行信息不完全的研发 QTE。
5. 研发达到 80 分后菜谱解锁，才能加入与店型兼容的菜单。客人绝大多数从菜单点菜，少量客人提供相邻节点线索。
6. 玩家选择日料、烧烤、火锅或小摊定位，设置市场大小、位置和等级，选择调料品质，雇服务员、厨师和店长。
7. 玩家划定市政功能区，处理价格波动、猪瘟、禽流感和特殊 NPC 事件，逐步开后台模拟分店。
8. 野采、报刊亭、厨师 PK、装修、节日和文化偏好共同提供新食材、厨师、食谱节点、顾客和品牌资源。
9. 玩家以赚钱和食品品牌为长期目标，经营主店和分店，培养招牌菜的全球影响力。
10. 品牌主流程完成后，可进入低 SAN 重演小镇。那里会重新启用熟练菜的 QTE，并按入锅变换规则制作阴暗菜；该内容不阻塞食品品牌终局。

第 2–10 步中所有 AI 补充的门槛、规模和数值都在 `docs/AI_FILLED_DETAILS.md`，尤其是 AI-001 至 AI-035。

## 4. 跨阶段数据链

### 4.1 食谱和熟练度

官方食谱使用 AI-001 的状态机。每个稳定 `recipe_id` 保存：

- 来源、文化、店型与菜系标签；
- 必需食材、允许替代、调料地域要求；
- 固定工序表、初学 QTE 表和研发 QTE 表；
- 研发图节点、前置节点、基础点数和相似度标签；
- 解锁状态、菜单状态、玩家熟练次数；
- 普通版本和可选阴暗版本映射。

自建食谱继续使用稳定 ID 和版本，但按 AI-006 与官方研发图隔离。

### 4.2 一盘菜

做菜核心继续输出大纲规定的六项属性：口味、温度、香味、口感、完成度和搭配度。客人评分只读成品和声明要求，不回写菜品。

固定程序不意味着写死菜名：

- 配置选择步骤和 QTE；
- 食材实例保存真实切型、份量、温度和处理历史；
- 通用工序应用 Modifier；
- 成品快照记录真实材料、步骤、反应和结果；
- 新机制可以增加代码，新菜优先只增加数据。

### 4.3 订单和选店

每家店有独立菜单，只含已解锁且与店型兼容的菜。NPC 先按单个“店 × 菜”计算：

`竞争优势 = 前菜品评价 + 前装修评价 + 前品牌评价`

再选择最高者。计算快照和平局使用 AI-016。菜单内外比例使用 AI-015。进店后仍沿用 Phase 3 的迎宾、入座、等菜、传菜、收银和评价状态。

### 4.4 时间

使用 AI-010：真实行为严格占用游戏内时间，但不与现实系统时钟同步。QTE 中游戏时间继续，主动暂停冻结游戏与操作时钟。备货、研发、事件、建设和休息通过活动令牌避免重叠扣时。

### 4.5 存档

- Phase 2 的 `user://shop-v1.json` 保持原边界。
- Phase 3 旧会话在新版世界存档建立前仍按当前实现运行。
- Phase 4 先实现 AI-019 的世界存档，再保存研发、熟练、市场、员工、店型、市政和事件。
- 影响钱、物品、评分和解锁的随机结果按 AI-030 首次生成后持久化。
- 每次 schema 变化都有迁移测试、备份、未知未来版本拒绝和重复调用幂等测试。

来源：大纲 §10 的技术原则、项目总控规范和 AI-031 的首发目标。

### Phase 6-0：冻结和缺陷分级

- 冻结主要功能和 active 内容；
- 按坏档/崩溃/终局阻断、经济漏洞、交互、表现四级处理；
- 每个修复先有复现，再补回归。

### Phase 6-1：自动验证

- 资源导入和生产资源加载；
- 全量单元、QTE、经营、餐厅、成长、事件和内容引用测试；
- 新档通关模拟、关键节点真实场景和存档迁移；
- 重复交付、日结、领奖、员工/玩家重复操作、负库存、刷市场和读档重抽攻击测试；
- 零测试、跳过、解析错误或超时均失败。

### Phase 6-2：目标机和人工验证

- 按 AI-031 检查启动、窗口/全屏、分辨率、输入、音频、暂停、失焦、减少动态效果；
- 实测长时间营业、小镇切换、双 QTE、满客餐厅和最大首发地图；
- 分别记录机器自动输入、实体键鼠、耳机/扬声器和真人玩法结果。

### Phase 6-3：性能、资产和包体

- 用真实 Profiler 记录帧时间、加载、内存和节点数；
- 核对资产许可证、署名、占位资产和敏感文件；
- 包内排除测试、原始设计资料、开发跳转、真实存档和私有信息。

### Phase 6-4：可重复发布候选

- 使用锁定 Godot 和导出模板；
- 在干净副本重做导入、测试和 Windows 导出；
- 记录版本、提交或工作树差异、命令、文件哈希和已知问题；
- 输出操作说明、存档兼容、回退限制和发布说明；
- 没有实体设备或完整人工通关证据时，只能叫“发布候选，尚未满足发布门槛”。

## 11. 三人并行和合并

Phase 4 延续 `docs/COLLABORATION.md` 的三线：

- 做菜与研发；
- 经济与供货；
- 小镇与事件。

Phase 5 仍保持三线，但每个工作单元只允许一个人拥有共享会话、世界存档、主入口和 `project.godot`。每波开始先写契约和红灯测试；各线完成独立套件后，在合并日由轮值集成者接主流程、跑全量并更新记录。

不能为了“让三个人都有活”同时改一个共享文件。人少时缩小当波，不跨目录顺手开发。

## 13. 阶段通用停止条件

每个 Phase 都必须：

1. 先确认当前状态和用户最新范围，不重做已完成系统；
2. 把来源、AI 编号、AC、实现和测试一一对应；
3. 接入真实入口，不以孤立函数或调试按钮冒充完成；
4. 分开报告规则测试、场景测试、目标机运行和人工试玩；
5. 更新准确断点并停止，不自动开始下一 Phase。
